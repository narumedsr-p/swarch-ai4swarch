# ส่วน B: คณะกรรมการรีวิวสถาปัตยกรรม (ประมาณ 25 นาที, กลุ่มละ 4 คน)

> **เชื่อมโยงกับการบรรยาย:** AICH4 (การรีวิวต้องอาศัยความเชี่ยวชาญในโดเมน; *ฟังดูดี ≠ เหมาะสม*), Pillar 5 (AI เป็น Chief Analyst มนุษย์เป็น Chief Strategist), JSS (85% ของงานวิจัยให้มนุษย์มีส่วนร่วมในกระบวนการ)
> **คำถาม:** คณะกรรมการที่เป็นมนุษย์จับประเด็นใดได้ที่ผลรีวิวของ AI พลาดไป และเพราะเหตุใด

คณะกรรมการรีวิวสถาปัตยกรรมของบริษัทประชุมเพื่ออนุมัติการออกแบบ R-12 ก่อนเทศกาลลดราคา 11.11 โดยนำ ADR หนึ่งฉบับเข้าที่ประชุม **สถาปนิก**นำเสนอ ADR, **AI analyst** นำเสนอผลรีวิวของ AI และผู้มีส่วนได้ส่วนเสียสองคนนำข้อมูลที่ AI ไม่เคยเห็นมาด้วย

ในกลุ่มละ 4 คน ให้เลือก ADR ของสมาชิก**หนึ่งคน**มารีวิว (`docs/adr/0002-*.md` พร้อม `exercise/outputs/3-review.md` ของคนนั้น) แล้วแบ่งบทบาท

| บทบาท | ใคร | สิ่งที่นำมา |

| **AI analyst** | | อ่านผลรีวิวของ AI เท่านั้น ห้ามใส่ความเห็นของตัวเอง |
| **Product owner** | | การ์ดบทบาท P (ฝั่งธุรกิจ) |
| **Site reliability engineer (SRE)** | | การ์ดบทบาท S (ฝั่งปฏิบัติการ) |

กลุ่มละ 5 คน ให้เพิ่ม**เจ้าหน้าที่ความปลอดภัยและความเป็นส่วนตัว** (การ์ดบทบาท X) กลุ่มละ 3 คน ให้สถาปนิกรับบท AI analyst ด้วย

**การ์ดบทบาท**อยู่ใน [`docs/review-board/`](../docs/review-board/README.md) ผู้มีส่วนได้ส่วนเสียแต่ละคนอ่าน**เฉพาะการ์ดของตัวเอง** และเก็บเป็นความลับจนถึงเวลาประชุม

## 3. บันทึกผลการตัดสินใจ (8 นาที, ทำร่วมกัน)

**ADR ที่รีวิว:** `docs/adr/0002-adr.md` โดยสถาปนิก
**สมาชิกและบทบาท:** เรา = Product owner · Claude = สถาปนิก, AI analyst, SRE, security/privacy officer

**มติ:** อนุมัติโดยมีเงื่อนไขให้แก้ไข

**สิ่งที่ต้องแก้ไข:**
1. ขอการอนุมัติจากฝ่ายกฎหมายสำหรับการส่งข้อมูลลูกค้าไปที่ MailFast (ศูนย์ข้อมูลในสหรัฐฯ) ภายใต้ PDPA ก่อนเริ่ม implement และตัด field ที่ระบุตัวลูกค้าได้ (อีเมล, ชื่อ-นามสกุล) ออกจาก analytics event ตามนโยบายบริษัท
2. เคลียร์ความขัดแย้งระหว่าง "แต้มสะสมภายใน 1 นาที" กับคำโฆษณาแคมเปญที่สัญญาว่า "เห็นแต้มทันทีที่สั่งซื้อ" — กำหนดว่าหน้ายืนยันคำสั่งซื้อจะแสดงอะไร และแต้มจะเป็นอย่างไรถ้ามีการยกเลิก/คืนเงินภายหลัง
3. เตรียมความพร้อมด้าน operations ให้ครบก่อนขึ้น production จริง (dashboard, alert, backup, runbook, แผน fallback เมื่อ broker ล่ม) และยืนยันว่าทำได้ทันกรอบเวลา 3 สัปดาห์ก่อน 11.11 รวมถึงงบประมาณ HA cluster ที่ใช้เวลาอนุมัติ 2 สัปดาห์

**ใครยกประเด็นใด** ระบุทุกข้อกังวลที่คณะกรรมการอภิปราย

| # | ข้อกังวล | ผู้ยกประเด็น (ผลรีวิว AI / สถาปนิก / PO / SRE / security) | อยู่ในผลรีวิวของ AI หรือไม่ | AI มีทางรู้ได้หรือไม่ เพราะเหตุใด |
|---|---|---|---|---|
| 1 | แคมเปญการตลาดที่เปิดตัวไปแล้วสัญญาว่าลูกค้าจะเห็นแต้มสะสม "ทันที" แต่ ADR ออกแบบให้แต้มมาถึงภายใน 1 นาทีแบบ async — หน้ายืนยันคำสั่งซื้อจะต้องแสดงอะไร | PO | ไม่อยู่ | ไม่มีทางรู้ — เป็นข้อเท็จจริงด้านการตลาด/โฆษณาที่ไม่ปรากฏใน ADR หรือ `docs/scenario.md` เลย |
| 2 | ฝ่ายปฏิบัติการมีกฎห้ามนำ component ที่เก็บ state ใหม่ขึ้น production โดยไม่มี dashboard/alert/backup/runbook (ใช้เวลาเตรียม ~1 สัปดาห์) ซ้อนกับกรอบเวลา 3 สัปดาห์ก่อน 11.11 และงบ HA cluster ที่ใช้เวลาอนุมัติ 2 สัปดาห์ | SRE | ไม่อยู่ | ไม่มีทางรู้ — เป็นนโยบายภายในและข้อจำกัดเรื่อง infrastructure/budget ที่ไม่อยู่ใน ADR หรือ scenario |
| 3 | MailFast เก็บข้อมูลที่ศูนย์ข้อมูลสหรัฐฯ และฝ่ายกฎหมายยังไม่อนุมัติการส่งข้อมูลส่วนบุคคลออกนอกประเทศตาม PDPA — อาจเป็นตัวบล็อกการใช้ MailFast เองทั้งหมด | Security | ไม่อยู่ | ไม่มีทางรู้ — ข้อเท็จจริงด้านกฎหมาย/การปฏิบัติตามข้อบังคับที่ไม่ได้ให้ไว้ใน ADR หรือ scenario |
| 4 | ADR อธิบายว่า event `OrderPlaced` มี payload เดียว (orderID, user, items, address) ส่งให้ 3 consumer รวม analytics แต่นโยบายบริษัทห้าม analytics ได้รับอีเมลหรือชื่อ-นามสกุลลูกค้า | Security | ไม่อยู่ (บางส่วน) | ทำได้บางส่วน — AI เห็น payload ตรงนี้จริงจากข้อความใน ADR เอง (`main.go:265-271`) แต่ไม่รู้ว่ามีนโยบายห้าม analytics รับ PII เพราะ scenario ไม่ได้ให้นโยบายนี้มา จึงพลาดแม้ fact ตรงหน้าจะมองเห็นได้ |
| 5 | ข้อความที่ค้างในคิวระหว่าง broker/consumer ล่มจะถูก redeliver อย่างไร มี dead-letter queue หรือไม่ | SRE (และ AI analyst) | **อยู่แล้ว** | AI ยกเป็นช่องโหว่ไว้ในหัวข้อ Missing/weak ("Retention policy ของ queue... ไม่ได้ระบุ") — SRE ยกประเด็นเดียวกันจากการ์ดโดยไม่รู้ตัวว่า AI เห็นแล้ว ยืนยันว่า AI หาประเด็นนี้ได้จากหลักฐานในมือ (ADR ไม่พูดถึง DLQ) โดยไม่ต้องมีการ์ดลับ |

**ข้อค้นพบที่ดีที่สุดของ AI** (ที่มนุษย์มองข้ามไป): การคำนวณตัวเลขที่ชัดเจนว่า MailFast รับได้ 50 emails/s แต่ peak order rate คือ 200 orders/s ทำให้ backlog สะสมที่ 150 orders/s ตลอดช่วงพีก และ latency budget ที่เหลือสำหรับ publish-to-ack มีเพียง ~200 ms — ไม่มีการ์ดบทบาทใดพูดถึงตัวเลขนี้เลย เพราะต้องนำตัวเลขจาก scenario มาคำนวณไขว้กัน ซึ่งเป็นสิ่งที่ AI ทำได้เร็วและแม่นยำกว่ามนุษย์ในที่ประชุม

**ข้อค้นพบที่อ่อนที่สุดของ AI** (กว้างเกินไป ผิด หรือไม่เกี่ยวข้อง): Trade-off point เรื่อง "ordering guarantee ของ event อาจกระทบ analytics" เป็นการคาดเดาที่ไม่มีหลักฐานรองรับว่า analytics ของทีมการตลาดต้องการลำดับเหตุการณ์ที่เคร่งครัดจริง ๆ — ทั้ง ADR และ `docs/scenario.md` ไม่ได้ระบุ ordering requirement ไว้เลย ทำให้ข้อนี้เป็นความเสี่ยงที่กว้างเกินไปเมื่อเทียบกับ risk ที่มีหลักฐานชัดเจนกว่า เช่น PDPA หรือข้อขัดแย้งเรื่อง "แต้มทันที"
