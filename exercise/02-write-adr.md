# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ _ครบถ้วนน้อยกว่ามนุษย์_ ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ใช้เลย — ไม่มี p95, peak rate หรือ rate limit ตัวใดๆ ทุกตัวเลขที่ขาดถูกยกไปไว้ใน Open questions แทน เพราะ run นี้ไม่มี context ให้อ่าน | ใช้ครบและอ้างอิงตรงจาก `docs/scenario.md` — p95 ≤ 500 ms (ปัจจุบัน ~300 ms), peak 200 orders/s, MailFast p95 1.5 s / p99 8 s / rate limit 50 emails/s, แต้มสะสมต้องให้ภายใน 1 นาที |
| ทางเลือกที่พิจารณา (ระบุ) | 1) Synchronous orchestration 2) Event-driven ผ่าน message broker (ไม่ระบุชนิดของ broker) 3) Batch/scheduled job | 1) ขยาย synchronous orchestration เดิม 2) Event-driven ผ่าน **RabbitMQ** โดยเฉพาะ (ระบุชนิด broker ชัดเจนเพราะรู้จาก scenario ว่าทีมมีประสบการณ์ RabbitMQ) 3) Fire-and-forget แบบ async โดยไม่มี broker |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | พูดถึงหลักการ idempotent consumer ไว้แบบกว้างๆ แต่ไม่มีกลไกที่เจาะจง (ไม่รู้ว่ามี `orderID` อยู่แล้วในโค้ด) และไม่พูดถึง rate limit ของ MailFast เป็นตัวเลขเลยเพราะไม่มีข้อมูล | ระบุกลไกเจาะจง — ใช้ `orderID` ที่มีอยู่แล้วใน `main.go:233` เป็น idempotency key ให้ `loyaltyservice` ตรวจก่อนให้แต้ม ส่วน MailFast พูดถึงว่าต้อง throttle ที่ 50/s แต่ร่างดิบของ AI ยังไม่ได้คำนวณตัวเลข backlog ที่แน่นอน (นิสิตเป็นคนคำนวณเพิ่มเองตอนแก้เป็นฉบับสุดท้าย) |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่พบ — ทุกอย่างที่ไม่รู้ถูกยกไปเป็น Open questions อย่างถูกต้อง ไม่มีการเดาตัวเลขหรือเทคโนโลยีที่ไม่มีหลักฐาน | พบคำกล่าวอ้างที่ผิด/เกินจริงหนึ่งจุด — ใน Decision เขียนว่าออกแบบนี้ "รองรับ exactly-once ของแต้มสะสม" ทั้งที่ RabbitMQ การันตีได้แค่ at-least-once เท่านั้น ไม่มีหลักฐานใน scenario รองรับคำว่า exactly-once เลย (นิสิตแก้จุดนี้แล้ว ดูตาราง "รับผิดชอบ ADR ฉบับสุดท้าย" ด้านล่าง แถวที่ 1) |

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| #   | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
| --- | --------------------------- | ------ |
| 1   | ตัด claim "รองรับ exactly-once ของแต้มสะสม" ออกจาก Decision และเขียนใหม่ให้ชัดว่า RabbitMQ การันตีได้แค่ at-least-once delivery ส่วนการให้แต้ม "ครั้งเดียว" มาจาก idempotent consumer ที่ `loyaltyservice` ตรวจ `orderID` ซ้ำเอง ไม่ใช่การันตีจาก broker | ร่างของ AI ใช้คำว่า exactly-once ซึ่งผิดหลักเทคนิคของ message broker ทั่วไป (รวมถึง RabbitMQ) อาจทำให้ผู้ฟังเข้าใจผิดว่า broker การันตีความถูกต้องของแต้มสะสมให้ ทั้งที่จริงภาระตกอยู่ที่การออกแบบ consumer ให้ idempotent — ต้องพูดให้ตรงเพื่อป้องกันคำถามจากคณะกรรมการว่า "แล้วถ้า broker ส่งซ้ำล่ะ" |
| 2   | แก้ risk เรื่อง MailFast backlog ให้มีตัวเลขคำนวณรองรับ (backlog สะสมที่ 200 − 50 = 150 orders/s) และระบุชัดว่ายังขาดตัวเลขความยาวของช่วงพีกจึงยังกำหนด queue depth/เวลาระบาย backlog ที่แน่นอนไม่ได้ (ทิ้งเป็น Open question) แทนที่จะพูดกว้าง ๆ ว่า "ต้อง throttle" | ร่างของ AI ระบุ risk ถูกต้องแต่ไม่ได้คำนวณอัตรา backlog ทั้งที่ข้อมูลมีพร้อมใน scenario การใส่เลขที่คำนวณได้จริงเข้าไปทำให้ risk นี้เป็นรูปธรรมและตรวจสอบได้มากขึ้น ส่วนตัวเลข queue depth/เวลาระบายที่เคยลองเติมเองในรอบแรกไม่มีหลักฐานรองรับ (มั่ว) จึงถอนออกและทิ้งเป็น Open question ตามหลัก evidence first แทน |
| 3   | เพิ่ม risk ใหม่เรื่อง "มีเพียง 2 จาก 4 คนที่มีประสบการณ์ RabbitMQ" พร้อม mitigation (ให้ 2 คนที่มีประสบการณ์ pair กับอีก 2 คนตลอดช่วง implement) | ร่างของ AI พูดถึงช่องว่างด้านทักษะทีมไว้แค่ใน Negative consequence (บรรทัดเดียว) แต่ไม่มี mitigation ทั้งที่เป็น risk ที่กระทบต่อ driver #5 (team skill) และคุณภาพของ consumer ที่ต้องเขียนใหม่ 3 ตัว ยกเป็น risk แยกพร้อม mitigation ที่ปฏิบัติได้จริง (pairing) เพื่อให้ตอบคณะกรรมการได้ว่าทีมมีแผนรับมือ ไม่ใช่แค่ยอมรับความเสี่ยงเฉย ๆ |
